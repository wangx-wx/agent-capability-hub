# Agent 能力中台产品规格（方向稿）

## 文档目的

本文记录产品方向、首期范围和已经讨论确认的行为，供后续选型、规划和实施时使用。它是产品规格，不指定最终技术栈、仓库结构或实现顺序。

管理员认证、用户/角色、API Key、Skills 可见性和首个实现阶段以 [管理员认证与首个业务阶段规格](../20261121-admin-auth-and-first-business-loop.md) 为准；本文相关旧决定已按该规格更新。

2026-11-22 补充：本轮真实 MCP 与 REST 接入的逐项澄清记录见 [MCP 网关与 REST 转 MCP 接入规格](../20261122-mcp-rest-integration.md)。各项选择已完成，整体规格待用户确认；本文保留方向与历史阶段说明，实施时再按确认后的接入规格落实。

## Problem Statement

团队开始使用 MCP 工具、REST API 和 Agent Skills 后，能力来源分散在不同的 MCP 服务、API 文档和 GitHub 仓库中。管理员难以统一登记可用能力、控制成员能调用哪些工具，也难以追溯 MCP 工具的使用者。用户则需要自行寻找 Skills、辨认适用于哪些 Agent，并手工配置 MCP 连接。

用户希望建设一个完全开源、可自托管的 Agent 中台：用一个控制台管理 MCP 与 REST 能力、角色授权和调用审计，同时提供公开的 Skills 广场。后续再增加 A2A Agent 注册、任务下发以及 Agent 之间讨论、实施和审核的能力。

## Solution

建设一个单组织、自托管的 Agent 能力中台。首期作为控制面和网关运行，不在平台服务器上启动或托管 Codex、Claude Code、Pi 等 Agent 进程。

平台由三个主要产品面组成：

1. **MCP 网关**：Agent/IDE 客户端通过 Streamable HTTP 接入。平台连接已有的 Streamable HTTP 或旧版 SSE MCP 下游，并把获准的工具聚合给调用者。
2. **REST 转 MCP**：管理员可从 OpenAPI JSON、OpenAPI YAML、cURL 导入 REST 操作，也可手动定义接口。登记后的 REST 操作映射为 MCP 工具。下游认证首期只支持无鉴权或服务级静态 HTTP 请求头。
3. **Skills 广场**：无需登录即可浏览。管理员配置希望展示的 GitHub 插件/Skill 来源；平台按 [GitHub 来源解析规格](../20261127-skills-github-discovery.md) 解析并展示可安装 Skills，但不 clone 仓库、不托管或下载 Skill 文件。用户复制标准 `npx skills@latest add` 命令，在自己的 Agent 环境中从来源仓库安装。

已认证的用户工作台与公开 Skills 广场是两个独立入口。用户工作台使用账号密码登录；API Key 只用于 MCP Bearer 鉴权。Skills 分为公开条目和仅登录用户可见的特殊条目，特殊条目可由角色控制可见性。

## User Stories

1. 作为平台管理员，我希望创建和维护用户，以便控制谁可以使用本部署中的 MCP 服务。
2. 作为平台管理员，我希望创建自定义角色，并给每位用户分配一个或多个角色，以便按岗位或职责管理 MCP 工具访问权限。
3. 作为平台管理员，我希望为角色配置可访问的 MCP 服务和具体工具，以便权限能够细到单个工具。
4. 作为平台管理员，我希望新工具默认不对任何角色开放，只有明确授权后才可用，以便服务更新不会意外扩大访问范围。
5. 作为 MCP 调用者，我希望工具列表只返回我的角色获准使用的工具，以便 Agent 不会把无权使用的工具当成可用能力。
6. 作为 MCP 调用者，我希望直接调用未授权工具也会被拒绝，以便隐藏工具列表不能被绕过。
7. 作为平台管理员，我希望固定管理员角色只绑定初始化账号，以便平台管理权限不会被普通角色意外授予。
8. 作为平台管理员或普通用户，我希望管理权限范围内的 API Key，以便用户自助配置 Agent 且管理员能够统一管理。
9. 作为 API Key 持有者或管理员，我希望重复复制已有 Key，以便无需因忘记保存而立即重新签发。
10. 作为普通用户，我希望用账号密码登录网页，并使用 API Key 通过 Bearer 认证，以便网页会话和 Agent 凭证相互独立。
11. 作为团队部署者，我希望本地身份认证不依赖企业 IdP，同时平台身份边界保留后续接入 OIDC/SSO 的扩展空间。
12. 作为平台管理员，我希望登记 Streamable HTTP MCP 下游，以便把远程 MCP 服务接入统一网关。
13. 作为平台管理员，我希望登记旧版 SSE MCP 下游，以便兼容尚未升级传输方式的现有 MCP 服务。
14. 作为平台管理员，我希望让 MCP 下游工具映射成平台服务和工具，以便复用角色授权和审计能力。
15. 作为平台管理员，我希望导入 OpenAPI JSON 或 YAML，以便快速把 REST API 操作转换为 MCP 工具。
16. 作为平台管理员，我希望导入 cURL 请求，以便把已有的 API 调用样例转成可配置的 MCP 工具。
17. 作为平台管理员，我希望手动定义 REST 操作的方法、路径、工具名、说明、参数 schema、必填项和请求体 schema，以便接入没有 OpenAPI 文档的 API。
18. 作为平台管理员，我希望为 REST 服务选择无鉴权或一组服务级静态 HTTP 请求头，以便覆盖首期的公开 API 和共享凭证 API 场景。
19. 作为 MCP 调用者，我希望通过 Streamable HTTP 连接中台并发现可用工具，以便常见 Agent/IDE 可以使用统一 MCP 地址。
20. 作为 MCP 调用者，我希望工作台展示网关地址、Bearer Key 用法和常见 Agent 配置片段，以便正确配置本地 MCP 客户端。
21. 作为平台管理员，我希望审计正式 MCP 工具调用的成功和失败，以便追踪能力使用情况和定位问题。
22. 作为审计查看者，我希望每条工具调用记录包含用户、MCP 服务、工具和发生时间，以便回答“谁在何时调用了哪个工具”。
23. 作为审计查看者，我希望在 MCP 客户端提供名称或版本时一并记录为来源 Agent 标签，以便辅助判断调用来自 Codex、Claude Code 或其他客户端。
24. 作为平台安全负责人，我希望来源 Agent 标签不替代 API Key 身份，以便自报客户端信息不能伪装真实调用者。
25. 作为平台安全负责人，我希望首期审计不保存工具参数和结果正文，也不记录工具搜索或管理员测试调用，以便控制审计数据敏感度和范围。
26. 作为 Skills 使用者，我希望无需登录即可浏览公开 Skills 目录，以便快速发现可安装的工作流能力。
27. 作为平台管理员，我希望配置希望在广场中展示的 GitHub 插件/Skill 来源，以便维护经过挑选的公开目录。
28. 作为 Skills 使用者，我希望看到由 GitHub 来源解析出的 Skill 信息和安装命令，以便直接从原仓库安装，而不依赖平台托管文件。
29. 作为 Skills 使用者，我希望复制 `npx skills@latest add` 安装命令后在本机执行，以便 Skill 安装到本机 Agent 能识别的位置。
30. 作为 Skills 使用者，我希望同一 Skill 尽可能通过通用 Skills 规范被多个 Agent 使用，以便减少为每种 Agent 重复安装和维护的工作。
31. 作为平台管理员，我希望控制 GitHub 来源中哪些插件/Skills 出现在广场，以便广场内容由管理员策展，而不是自动公开所有发现项。
32. 作为 Agent 平台使用者，我希望后续能登记 Codex、Claude Code、Pi 等 A2A Agent 并下发任务，以便把多个 Agent 组织成协作流程。
33. 作为 Agent 平台使用者，我希望后续能让一个 Agent 讨论方案、另一个 Agent 实施、再由其他 Agent 审核，以便形成可追踪的多 Agent 工作流。

## Implementation Decisions

### 产品边界

- 每个自托管部署只有一套用户与角色空间，不建立组织或团队层级。部署者直接启动平台；容器编排、操作系统和具体安装形态属于技术选型阶段。
- 固定管理员角色只绑定环境变量初始化的管理员账号；该账号自动拥有全部菜单、MCP/工具和特殊 Skills 权限。
- 管理员可创建普通角色；普通用户至少持有一个普通角色，可以持有多个，授权取并集。普通角色不能获得用户或平台管理权限，也不单独配置菜单权限。
- 普通角色的 MCP 服务/工具授权同时控制可见性与调用权限，未授权默认拒绝。角色仍分配给用户时不得删除。
- MCP `tools/list` 只呈现调用者角色获准且服务当前可用的工具。调用入口必须再次执行同一授权判断，不能把隐藏列表当成安全边界。

### 身份与 API Key

- 首期使用平台本地账号密码，不实现企业 OIDC/SSO 登录；身份接口和认证边界应允许后续增加 OIDC/SSO 提供方。空数据库从 `.env`/环境变量初始化唯一管理员；缺少初始化凭证时拒绝启动，管理员后续通过本机 CLI 重置密码。
- 管理员创建用户时系统生成随机初始密码并仅在创建完成时展示一次。普通用户可用当前密码自行改密，管理员可重置普通用户密码；凭证变更注销该用户全部网页会话。
- 网页使用账号密码登录，固定会话时长为 12 小时；API Key 只用于 MCP Bearer 鉴权。用户管理自己的 Key，管理员管理所有用户的 Key。
- 每个用户可创建多个具名 Key；创建时必须明确选择过期时间或永久有效。Key 明文存入 SQLite，用户本人和管理员可重复复制；停用用户的所有 Key 永久失效，重新启用后需重新创建。
- 用户 API Key 是调用者身份的权威来源。MCP 客户端初始化信息中的名称/版本只作为可选来源标签，不用于身份认证或授权。

### MCP 与 REST 能力模型

- 上游（Agent/IDE 到平台）首期只提供 Streamable HTTP MCP。
- MCP 下游首期只接 Streamable HTTP 和旧版 SSE，不支持 stdio 子进程。
- REST API 注册后映射成 MCP 服务下的工具，统一进入角色授权和 MCP 调用审计流程。
- REST 导入来源包括 OpenAPI JSON、OpenAPI YAML 和 cURL；同时提供手动操作定义。手动操作至少包含 HTTP 方法、相对路径、工具名、说明、参数 schema、必填参数和请求体 schema。
- REST 下游认证只支持无鉴权或服务级静态 HTTP 请求头；同一服务的操作共享该配置。首期不支持 OAuth、按用户凭证、query 参数鉴权或其他凭证策略。
- OpenAPI/cURL 的导入预览、schema 推断边界、文件/文本/URL 输入方式、冲突处理和版本更新规则尚未确定，进入实施规划前细化。

### 审计

- 只审计正式工具调用，不审计工具搜索、管理 API 读取/写入或管理员测试调用。
- 成功和失败调用都写审计记录。首期字段为用户、MCP 服务、工具、时间；存在 MCP 客户端名称/版本时可添加来源 Agent 标签。
- 不记录工具参数和工具结果正文。失败原因、HTTP 状态、耗时、请求 ID、来源 IP、审计保留与清理周期尚未确定，不应未经确认扩大到首期记录字段。

### Skills 广场

- GitHub 来源地址的发现边界、无 clone 解析流程与 `skills@1.9.0` 默认发现规则以 [Skills 广场 GitHub 来源解析规格](../20261127-skills-github-discovery.md) 为准。
- 公共 Skills 可公开浏览；特殊 Skills 仅登录可见，并按普通角色授权过滤。固定管理员角色可见全部特殊 Skills。
- 管理员登记/策展 GitHub 插件/Skill 来源；平台只解析展示条目，不托管源文件、不下载 Skill 完整内容。安装由用户本地 `skills` CLI 直接从 GitHub 来源完成。
- 展示页面和安装命令属于产品能力，但具体元数据字段尚未确定，用户明确留待后续讨论。
- 广场首期以 `npx skills@latest add` 安装命令为准；解析规则对齐 npm `skills@1.9.0`，不启用会要求完整检出仓库的 `--full-depth` 模式。
- 仓库采用哪个分支、tag 或 commit，以及如何刷新目录版本，留到实施时讨论。平台不替用户选择或下载 Skill 版本。
- Skill 内容遵循公开的 Agent Skills 规范，不另创一套文件格式。

### 工作台与 A2A 阶段

- 普通用户使用账号密码登录工作台；API Key 用于 Bearer 鉴权。首个实现阶段只通过只读 API 返回获授权的 demo 服务、工具和 Skills 条目，不执行工具调用。
- Skills 广场与登录工作台分离，未登录用户也能访问公开目录和复制安装命令。
- 首期不运行或托管 Agent 进程，不实现 A2A Agent 注册、任务管理、讨论、实施或审核流程。
- 后续 A2A 阶段目标包括登记 Agent、下发任务，以及多 Agent 讨论方案、实施和审核；协议兼容范围、Agent 执行环境、安全隔离、任务状态与人工审批均需独立规格。

## 首个实现阶段验收结果

1. 空 SQLite 数据库从 `.env`/环境变量创建唯一管理员；缺少凭证时服务拒绝启动，已有管理员不受环境变量变更影响。
2. 管理员可创建、停用和重新启用普通用户，创建角色并分配多角色；用户可账号密码登录和修改自己的密码。
3. 管理员与用户按权限创建和管理 API Key；Key 可设过期或永久有效，明文存入 SQLite 并可重复复制。
4. 用户的多个角色授权取并集；Bearer 只读 API 返回该用户获准的 demo 服务、工具和 Skills 条目。
5. 密码变更注销所有网页会话；账号停用永久使既有 Key 失效；本阶段不执行 MCP 工具调用。

## 后续完整产品阶段目标

完整产品阶段完成后，应能演示以下端到端产品结果：

1. 管理员创建用户和角色，为角色授权指定服务中的指定工具，并创建 API Key。
2. 管理员登记 Streamable HTTP 或旧版 SSE MCP 服务，或从 OpenAPI JSON/YAML、cURL、手动表单建立 REST-to-MCP 服务。
3. 用户使用账号密码登录工作台，使用 API Key 连接 MCP 网关；工具列表只显示角色允许的工具，未授权工具即使通过名称直接调用也不能执行。
4. 正式 MCP 工具调用成功或失败时产生审计记录，记录能回答调用者、服务、工具和时间；参数及结果正文不进入审计。
5. 未登录访客可浏览管理员策展的 Skills 条目并复制安装命令；Skill 文件仍由 GitHub 来源提供，平台不存储或下载文件。
6. A2A Agent 协作不属于首期验收范围。

## Out of Scope

- A2A Agent 控制台、Agent 运行环境、任务编排、多 Agent 讨论/实施/审核。
- 平台服务器托管或启动 Codex、Claude Code、Pi 等 Agent 进程。
- 多组织/多租户隔离、团队实体。
- 企业 OIDC/SSO 的首期实现；首期只保留扩展方向。
- stdio MCP 下游、stdio MCP 上游。
- REST OAuth、query 鉴权、每用户凭证、多个下游身份策略。
- Skills 文件托管、文件下载、代理安装、平台写入用户本机 Agent 目录。
- 特殊 Skills 的 GitHub 来源集成、导入和完整广场交互属于后续阶段；公开 Skills 不需要登录，特殊 Skills 按本规格进行登录和角色过滤。
- MCP 搜索、管理测试、管理 API 请求进入首期调用审计。
- Skills 页面完整交互与展示字段、来源缓存/刷新时效的具体定案。
- 最终技术栈、系统架构和代码组织方式；此项属于下一阶段技术选型。

## Further Notes

- 本文使用以下领域词汇：**服务**是已登记的 MCP 或 REST 下游能力集合；**工具**是服务暴露给 MCP 调用者的单个操作；**角色**是用户可获得的工具授权集合；**调用者**由 API Key 识别；**审计**记录正式工具调用的基本事实。
- “来源 Agent”可从 MCP 客户端初始化信息取得名称/版本并作辅助标注；该信息由客户端自报，可信度低于 API Key。
- 本文明确保留为后续讨论的事项：Skills 广场页面交互与完整元数据、来源缓存/刷新策略、OpenAPI/cURL 导入细节、审计保留周期与额外字段。
- 2026-11-27 修订：Skills GitHub 来源发现和 `skills@1.9.0` 行为已完成调研，详见[专用规格](../20261127-skills-github-discovery.md)。本规格替代原先“安装器解析能力尚未调研”的条款；规格没有涵盖的来源授权和缓存细节仍待实施前决定。
